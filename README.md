# Music Room — LAN MVP

یک اتاق موسیقی برای شبکه داخلی با FastAPI، صف MP3 مشترک، مدیر، و پخش روی مرورگر موبایل. **هیچ ضبطی از صدای ویندوز انجام نمی‌شود** و کامپیوتر اصلی لازم نیست. منبع صدا فقط فایل‌های آپلودشده روی سرور Ubuntu است.

## اجرا روی Ubuntu (Docker)

```bash
cp .env.example .env
# رمز مدیر، رمز دیتابیس و کلیدهای تصادفی را در .env تنظیم کنید
nano .env
docker compose up -d --build
docker compose logs -f
```

آدرس: `http://SERVER_LAN_IP:8000` (همه کاربران و مدیر از همین صفحه وارد می‌شوند.) برای ورود مدیر در بخش «مدیریت» رمز را وارد کنید.

اگر پورت ۸۰۰۰ اشغال است، مقدار `MUSIC_PORT` را در فایل `.env` به یک پورت آزاد (مثلاً `8088`) تغییر دهید، دوباره `docker compose up -d` را اجرا کنید و با پورت جدید مراجعه کنید. اگر فایروال UFW فعال است: `sudo ufw allow from YOUR_LAN_SUBNET to any port 8000 proto tcp`؛ شماره پورت را مطابق تنظیم خود جایگزین کنید و آن را صرفاً برای شبکه مجاز باز کنید.

## حساب‌های ساخته‌شده توسط مدیر

ثبت‌نام عمومی بسته است. صفحه `/login` فقط نام کاربری و رمز حساب موجود را قبول می‌کند. مدیر در بخش مدیریت، فرم «ساخت کاربر» را پر می‌کند و نام کاربری و رمز انتخابی را به کاربر می‌دهد.

- جدول PostgreSQL `users` نام کاربری، هش salted scrypt رمز و نقش مدیر را نگه می‌دارد؛ رمز خام ذخیره یا در API برگردانده نمی‌شود.
- `MUSIC_ADMIN_USERNAME` نام حساب مدیر اولیه است (پیش‌فرض `admin`). در اولین راه‌اندازی، رمز این حساب از `MUSIC_ADMIN_PASSWORD` گرفته می‌شود. سپس با همین حساب وارد شوید و بخش مدیریت را باز کنید.
- `MUSIC_SESSION_SECRET` حداقل ۳۲ کاراکتر و `MUSIC_DB_PASSWORD` رمز داخلی دیتابیس است.
- نشست‌ها ۳۰ روزه، HttpOnly و SameSite هستند؛ ده تلاش ناموفق در ده دقیقه محدودیت ورود ایجاد می‌کند.
- مهاجرت، نشست‌های مدل پین مشترک را باطل می‌کند. حساب‌های قبلی بدون رمز غیرفعال می‌مانند؛ مدیر با ساخت کاربر با همان نام به آن‌ها رمز می‌دهد و شناسه و واکنش‌های قبلی حفظ می‌شوند.
- نام هر آهنگ در `tracks` و واکنش‌ها در `reactions` ذخیره می‌شوند؛ `play_history` واکنش را به آهنگ و نوبت پخش وصل می‌کند. تغییر واکنش جایگزین انتخاب قبلی همان نوبت می‌شود و حذف واکنش آن را پاک می‌کند.
- کاربران فقط تعداد واکنش‌ها و انتخاب خود را می‌بینند. گزارش «چه کسی چه واکنشی زده؟» در مدیریت، آخرین ۱۰۰۰ واکنش را با نام آهنگ و کاربر نشان می‌دهد. API گزارش نیازمند توکن مدیریت است و اطلاعات هویتی در پخش عمومی WebSocket ارسال نمی‌شود.

برای اعمال نسخه جدید: `docker compose up -d --build`. مقدار `MUSIC_SHARED_PIN` دیگر استفاده نمی‌شود. اطلاعات موسیقی و واکنش‌های قبلی حفظ می‌شوند.

سرویس `users-db` PostgreSQL 17 را با Volume دائمی `users-db-data` و بدون پورت عمومی اجرا می‌کند. تمام جدول‌های کاربران، نشست‌ها، آهنگ‌ها، واکنش‌ها، صف، وضعیت پخش، تاریخچه و چت در دیتابیس `music_room` هستند. برای پشتیبان‌گیری:

```bash
docker compose exec -T users-db pg_dump -U music_room music_room > music-room-users.sql
```

## امکانات
- بخش «کاربران آنلاین» در مدیریت، کاربران دارای اتصال فعال به اتاق و نوع تقریبی دستگاه، سیستم‌عامل و مرورگر هر اتصال را هر ۵ ثانیه نمایش می‌دهد. تب‌های متعدد جدا نشان داده می‌شوند؛ شمارش کاربران یکتا است. این اطلاعات فقط برای حساب مدیر با توکن مدیریت قابل دریافت است. قطع اتصال پس از تشخیص سرور از فهرست حذف می‌شود؛ آنلاین بودن به معنای پخش صدا نیست.
- کاربر با واردکردن نام خودش MP3 بدون سقف حجم تعیین‌شده در برنامه آپلود می‌کند، فایل روی Volume سرور ذخیره شده و به انتهای صف افزوده می‌شود. نام هنگام ورود اجباری است؛ نام خالی، Guest، gust و مهمان پذیرفته نمی‌شود. چت و آپلود همیشه نام حساب واردشده را از سرور دریافت می‌کنند.
- امکان انتخاب چند MP3 و افزودن همه با یک کلیک وجود دارد. فایل‌ها به ترتیب ارسال می‌شوند و پیشرفت و نتیجهٔ هر فایل جدا نمایش داده می‌شود. تکراری بودن یا خطای یک فایل مانع ادامهٔ بقیه نمی‌شود.
- آهنگ‌های صف به ترتیب، خودکار پخش می‌شوند. با نبود آهنگ فعال، اولین آپلود فوراً شروع می‌شود.
- ساعت مشترک سرور مبنای پخش است. WebSocket هر ثانیه state را ارسال می‌کند و مرورگر با seek اصلاح می‌کند.
- مدیر: play / pause / next / seek / حذف از صف؛ فقط مدیر توکن کنترل می‌گیرد.
- مدیر می‌تواند با دکمه‌های بالا و پایین کنار هر آهنگ، ترتیب صف را تغییر دهد. ترتیب جدید برای همه نمایش داده می‌شود و باقی می‌ماند؛ جابه‌جایی دستی شافل را خاموش می‌کند تا پخش مطابق ترتیب انتخاب‌شده باشد.
- مدیر می‌تواند شافل را روشن یا خاموش کند؛ در حالت روشن، آهنگ بعدی به‌صورت تصادفی از صف انتخاب و از آن خارج می‌شود. آهنگ جاری تغییر نمی‌کند و تنظیم شافل بعد از ری‌استارت باقی می‌ماند. با خاموش کردن شافل، آهنگ‌های باقی‌مانده طبق ترتیب ذخیره‌شدهٔ صف پخش می‌شوند.
- فایل تکراری با مقایسهٔ محتوای فایل شناسایی می‌شود، حتی اگر نام آن تغییر کرده باشد. تا وقتی آهنگ در صف یا در حال پخش است، آپلود مجدد با پیام فارسی رد می‌شود. بعد از خروج از صف یا پایان پخش، افزودن دوباره از فایل ذخیره‌شده استفاده می‌کند و نسخهٔ اضافی روی دیسک نمی‌سازد. نسخه‌های با انکود یا تگ متفاوت، فایل متفاوت محسوب می‌شوند.
- هر گوشی یک بار باید «شروع شنیدن» را بزند، چون مرورگر پخش خودکار صدای بدون تعامل را مسدود می‌کند.
- آرشیو همهٔ آهنگ‌ها با جست‌وجو، دانلود و افزودن دوباره به صف در صفحهٔ اصلی در دسترس است. جلوگیری از تکرار برای افزودن از آرشیو و تاریخچه نیز اعمال می‌شود.
- تاریخچهٔ هر نوبت پخش شامل زمان شروع، زمان پایان و نتیجه (جاری، پخش کامل یا ردشده) در دیتابیس ذخیره می‌شود. مکث و ادامه، یک نوبت جدید محسوب نمی‌شوند. تاریخچه از زمان نصب این قابلیت ثبت می‌شود؛ سابقهٔ پخش‌های قبل از آن موجود نیست.

- برای هر نوبت پخش، سه واکنش 🔥 عالیه، ❤️ دوستش دارم و ⏭ بعدی در دسترس است. شمارش زنده برای همه و در بخش مدیر نمایش داده می‌شود؛ واکنش‌ها آهنگ را خودکار رد نمی‌کنند. هر کاربر یک واکنش دارد و می‌تواند آن را عوض یا حذف کند. واکنش‌ها با ری‌استارت باقی می‌مانند و نوبت پخش جدید شمارش مستقل دارد.
- زمان گذشته و مدت کل آهنگ، زیر تایم‌لاین پلیر نمایش داده می‌شود.
- باکس «گپِ اتاق» پیام‌ها را با نام و زمان به‌صورت زنده برای کاربران متصل نشان می‌دهد. ۱۰۰ پیام آخر در دیتابیس باقی می‌مانند و هنگام ورود یا اتصال مجدد بارگذاری می‌شوند. هر پیام حداکثر ۵۰۰ کاراکتر دارد و فاصلهٔ ارسال‌ها برای هر کاربر حداقل دو ثانیه است. Enter پیام را می‌فرستد و Shift+Enter سطر جدید می‌سازد.

## رابط کاربری

رابط Next.js فارسی و راست‌به‌چپ با منوی کناری، آرشیو کارت‌محور و پلیر ثابت پایین صفحه ارائه می‌شود. میز دی‌جی در تب مدیریت است. در موبایل ناوبری پایین صفحه قرار دارد و تنظیم کاهش حرکت دستگاه رعایت می‌شود. فونت وزیرمتن و تمام فایل‌های ظاهری روی خود سرور میزبانی می‌شوند و برای نمایش به اینترنت نیاز ندارند. مجوز فونت در `frontend/public/static/fonts/OFL.txt` موجود است.

## ذخیره‌سازی دائمی

- همهٔ MP3های پذیرفته‌شده در `data/music/` در مسیر پروژه ذخیره می‌شوند؛ نام فایل روی دیسک شناسهٔ یکتا است و نام اصلی در آرشیو و دیتابیس نگهداری می‌شود.
- PostgreSQL مرجع تمام داده‌هاست. جدول‌های `tracks`، `reactions`، `play_history`، `queue`، `state` و `chat_messages` کنار `users` قرار دارند. `reactions.user_id` کلید خارجی کاربران است؛ برای واکنش‌های کاربران حذف‌شده خالی می‌ماند و شناسه قدیمی در `listener_id` حفظ می‌شود.
- در اولین اجرای نسخه جدید، داده‌های `data/music.db` در یک تراکنش منتقل می‌شوند. جدول `storage_migrations` از انتقال تکراری جلوگیری می‌کند؛ SQLite پس از انتقال فقط نسخه قدیمی پشتیبان است و برنامه در آن نمی‌نویسد.
- پایان پخش و حذف از صف، فایل آهنگ را حذف نمی‌کند. داده‌ها با ری‌استارت یا بازسازی کانتینر باقی می‌مانند، چون پوشهٔ `data` روی میزبان به `/srv/data` متصل است.
- برای پشتیبان‌گیری کامل، فایل‌های `data/music/` را همراه یک نسخهٔ سازگار از دیتابیس نگه دارید؛ از PostgreSQL با `pg_dump` پشتیبان بگیرید و پوشهٔ موسیقی را هم نگه دارید.

## محدودیت‌ها
- این یک MVP برای LAN قابل اعتماد است، نه پخش نمونه‌برداری دقیق هم‌زمان. تفاوت تأخیر Bluetooth و بافر گوشی‌ها ممکن است قابل شنیدن باشد.
- با خاموش شدن صفحه یا محدودسازی مرورگر در پس‌زمینه، پخش می‌تواند متوقف شود.
- HTTP رمزنگاری نشده است: رمز ادمین و توکن روی شبکه قابل شنود هستند. صرفاً در شبکه مورد اعتماد استفاده کنید و به اینترنت Publish نکنید. برای انتشار خارج از شبکهٔ مورد اعتماد، HTTPS، احراز هویت شخصی و محدودیت آپلود لازم است.
- مدت MP3 بر اساس metadata استخراج می‌شود؛ برخی فایل‌های VBR ممکن است دقت پایین‌تری داشته باشند.
- هنگام ری‌استارت سرویس، پخش جاری متوقف می‌شود و مجدداً با دکمه Play ادامه پیدا می‌کند. صف و فایل‌ها باقی می‌مانند.
- برای حجم و تعداد آپلود سقفی در برنامه تعیین نشده؛ ظرفیت عملی به فضای ذخیره‌سازی سرور وابسته است.

## اجرای محلی بدون Docker

```bash
# Node.js 22 لازم است؛ خروجی فرانت توسط FastAPI ارائه می‌شود.
npm --prefix frontend ci
npm --prefix frontend run build
pip install -r backend/requirements.txt
export MUSIC_ADMIN_PASSWORD='your-password'
export MUSIC_ADMIN_TOKEN='your-long-secret-token'
export MUSIC_ADMIN_USERNAME='admin'
export MUSIC_SESSION_SECRET='replace-with-at-least-32-random-characters'
export MUSIC_DB_HOST='127.0.0.1'
export MUSIC_DB_PORT='5432'
export MUSIC_DB_NAME='music_room'
export MUSIC_DB_USER='music_room'
export MUSIC_DB_PASSWORD='your-postgres-password'
# دیتابیس و کاربر بالا باید از قبل در PostgreSQL ساخته شده باشند.
uvicorn backend.app.main:app --host 0.0.0.0 --port 8000
```

## آزمون‌ها

`npm --prefix frontend test` تست‌های انتقال وضعیت اتاق و آپلود چندفایلی را اجرا می‌کند. `npm --prefix frontend run typecheck` بررسی TypeScript و `npm --prefix frontend run build` بیلد تولید را اجرا می‌کند. تست‌های Python با `python -m unittest discover -s tests -v` اجرا می‌شوند؛ برای تست‌های ورود، `httpx==0.28.1` و یک PostgreSQL آزمایشی لازم است. تست‌های ورود فقط وقتی `MUSIC_DB_NAME` با `music_room_auth_test` شروع شود فعال می‌شوند و جدول‌های همان دیتابیس آزمایشی را پاک می‌کنند؛ از دیتابیس واقعی برای تست استفاده نکنید.


## ساختار کد

برای رفع timeout دانلود از `files.pythonhosted.org`، بیلد Docker Compose به‌صورت پیش‌فرض از mirror علی‌بابا (`https://mirrors.aliyun.com/pypi/simple/`) استفاده می‌کند. آدرس مخزن را می‌توانید با `MUSIC_PIP_INDEX_URL` در `.env` تغییر دهید؛ برای مخزن اصلی مقدار `https://pypi.org/simple` را بگذارید. پس از تغییر، `docker compose up -d --build` را اجرا کنید. نسخه‌های وابستگی‌های اصلی و بررسی گواهی HTTPS حفظ شده‌اند.

- `frontend/app/`: صفحات Next.js App Router با TypeScript و طراحی راست‌به‌چپ.
- `frontend/components/`: پلیر سراسری، چت، آرشیو، آپلود، واکنش‌ها و مدیریت.

مدیر پس از ورود به پنل مدیریت می‌تواند در تب «متن کارت»، تیتر بزرگ کارت سبز را تغییر دهد. متن در PostgreSQL ذخیره می‌شود و هم‌زمان برای کاربران متصل نمایش داده می‌شود؛ دکمهٔ «متن پیش‌فرض» بازگرداندن تیتر اولیه را آماده می‌کند و با «ذخیرهٔ تیتر» اعمال می‌شود.

در تب «کاربران»، مدیر می‌تواند حساب جدید بسازد یا با دکمهٔ ویرایش کنار هر کاربر، نام کاربری و رمز او را تغییر دهد. خالی گذاشتن رمز جدید، رمز فعلی را حفظ می‌کند؛ تغییر رمز نشست‌های فعال همان کاربر را می‌بندد.
- `frontend/lib/`: قرارداد API، اتصال WebSocket، همگام‌سازی صدا و منطق آپلود.
- `frontend/public/`: فونت محلی، آیکن‌ها، manifest و صفحهٔ آفلاین.
- `frontend/out/`: خروجی تولیدی `next build` (در Git ثبت نمی‌شود).
- `backend/app/`: کد Python و FastAPI شامل API، WebSocket، احراز هویت و ذخیره‌سازی.
- `backend/requirements.txt`: وابستگی‌های بک‌اند.
- `tests/`: تست‌های بک‌اند و JavaScript.
- `data/`: داده‌ها و فایل‌های موسیقی؛ مسیر آن تغییر نکرده است.

دستورهای نصب و اجرا را از ریشهٔ پروژه اجرا کنید. فرانت با Next.js و React ساخته و به‌صورت static export توسط FastAPI ارائه می‌شود؛ Node فقط برای ساخت لازم است. مسیرهای `/`، `/login` و `/admin/music` به خروجی Next متصل‌اند؛ فایل‌های عمومی در `/_next/static/` و `/static/` قرار دارند. داده‌های خصوصی و همهٔ APIها همچنان زیر کنترل نشست بک‌اند هستند. ارتباط API و WebSocket هم‌دامنه است و نیازی به CORS یا سرویس Node جداگانه نیست. Docker با یک مرحلهٔ Node فرانت را می‌سازد و فقط خروجی آن را وارد تصویر Python می‌کند.

برای نصب به‌صورت PWA از HTTPS (یا localhost) و مرورگر سازگار استفاده کنید. Service Worker فقط صفحهٔ عمومی قطع اتصال را ذخیره می‌کند؛ پیام‌ها، نشست‌ها، API و فایل‌های موسیقی آفلاین ذخیره نمی‌شوند. پخش زنده به اتصال سرور نیاز دارد. تغییر تب‌های داخلی پلیر را نگه می‌دارد؛ با قطع WebSocket صدا تا اتصال مجدد مکث می‌شود.

در توسعه، پس از تغییرات `npm --prefix frontend run build` را اجرا کنید و از پورت FastAPI استفاده کنید تا ورود و WebSocket هم‌دامنه بمانند. پیش‌نمایش مستقل `next dev` فقط فرانت است و API بک‌اند را ارائه نمی‌کند.

نسخهٔ قبلی فرانت برای بازگشت محلی در `migration-backups/pre-next-frontend/` نگه داشته شده و وارد تصویر Docker نمی‌شود.

### اصلاح بک‌اند بدون دسترسی به Docker Hub

اگر فقط کد بک‌اند تغییر کرده و وابستگی‌های Python و فرانت‌اند همان نسخهٔ قبلی هستند، از ایمیج موجود استفاده کنید:

